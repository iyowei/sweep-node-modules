# 架构总览: 程序设计范式与代价

> **状态**: 已定稿 (Accepted)
> **日期**: 2026-09-24
> **决策者**: 沈委
> **父文档**: [设计总纲](sweep-node-modules-design.md)
>
> 用途: 横向视图, 讲这套代码「怎么组织的、为什么这么组织」, 面向第一次读这个仓库的技术读者。
> 范围: 各分册讲「这个工具的设计是什么」(命令面 / 配置 / 扫描 / 删除); 本文只归纳背后的程序设计范式与代价, 不复述分册细节。
> 权威: 行为与决策的权威在 `docs/designs/` 各分册与 `docs/adrs/`; 本文属解释性归纳。

sweep-node-modules 干的活很朴素: 找到工作区 (一个装着多个项目的上层目录) 里散落的 `node_modules`, 量出体积, 删掉它们。

但翻一遍 `src/` 会发现, 这套代码的重心不在「删」。

> 它的重心在「凭什么说它删得对」: 谁上场由实测数据裁定, 行为对错由编号条款与金样本语料验收, 危险动作用四道不变量加逐级复核拦着, 连「名单写错了」都有专门的告警通道。

本文回答一个问题: 这套代码用了哪些程序设计范式 (分层、设计模式、数据结构、设计原则), 以及这些选择各要人付出什么。前一半是骨架, 后一半是账单, 两边都不省略。

## 先看骨架: 四层与一条数据流

一次 `sweep-nm --yes` 的运行路线是固定的:

参数解析 → 配置定位与装载 → 扫描 → 体积统计 → 预览渲染 → 安全闸校验 → 删除 → 执行报告。

沿着这条路线, 代码摊成四层。这是「扫描与体积」这条主线的剖面:

```text
cli.ts                          入口编排: 参数 / 配置 / 分流 / 退出码
  ↓
scan.ts / size.ts               门面: 对外只暴露胜出的那个候选
  ↓
scan-{prune,native,parallel}    候选实现: 同一接口, 多个实现
size-{du,js}
  ↓
runtime.ts                      适配层: Bun 与 Node 的差异全收敛于此
```

每层只解决一个问题。编排层解决「流程怎么串」, `cli.ts` 把这条原则写进了头注释: 「业务全在模块内, 本层只做接线与退出码」。门面层解决「对外露哪张脸」: `scan.ts` 整个文件的有效代码只有一行, 把胜出的并行扫描改名成 `createScanner`, 换候选只改这一行。候选层解决「同一件事用哪种做法做」: 五个实现各写各的, 但都实现 `types.ts` 里同一套 `Scanner` / `Sizer` 接口。适配层解决「环境差异谁来扛」: Bun 与 Node 的两处实质差异 (子进程 spawn 与文件读写) 全部收敛在 `runtime.ts` 内部, 调用方无感。

这张图是主线的剖面, 不是全仓的目录表。配置 (`config.ts` / `init.ts`)、渲染 (`render.ts`)、安全闸 (`guard.ts`)、删除 (`delete.ts`) 这些工序模块由编排层直接调度, 没有自己的门面与候选。门面与候选是为「多实现竞争」准备的, 没有竞赛的能力不需要赛道。

分层的实效, 可以拿「改动落在哪儿」来量: 改扫描策略, 碰候选与门面; 改删除语义, 只碰 `delete.ts`; 增删运行时的差异处理, 只碰 `runtime.ts`。跨层引用也不禁止, 但每一处都说得出来理由: 扫描候选要去安全闸取 `dedupeKey` 当去重键, 为的是让「扫描判两条」与「安全闸判重复」用同一个判定。这两处曾经各写一遍, 于是在同一条目录的大小写两种拼写下, 扫描判成两条、安全闸判成重复, 两边结论打了起来。

这也不是教科书里的分层架构, 没有「每层只准依赖下一层」的教条, 没有抽象的层间协议。它更像一条离环境由远及近的阶梯: 顶上排流程, 底下接运行时与文件系统; 流程变了动上层, 环境变了动下层。

## 候选制: 由数据裁定

这套代码里最不多见的一件事, 是候选制。

同一项能力不写一份实现, 写几份, 让它们竞争。扫描有三个候选: 手写剪枝递归 (`scan-prune`)、原生递归加后过滤 (`scan-native`)、有界并发 (`scan-parallel`)。体积统计有两个: 系统 `du` 快路径 (`size-du`) 与纯实现 (`size-js`)。

竞争有明确的赛制。先是资格赛: 全部候选用同一套行为契约用例考 (同一个循环把每个候选都注册一遍), 必须给出同一批结论, 过不了的直接出局。过了资格赛的进基准环节, 在同一批数据上计时, 成绩追加进 `bench/results/bench.jsonl` 存档, 口头结论不作数。基准还带一条记账纪律: 每轮跑完对比存档, 连续 3 轮没有收益就收口。

扫描的裁定结果是: 有界并发胜出。真实工作区 (约 3.8 万目录) 的扫描耗时从 3.4 秒降到 0.67 秒上下, 约 4.8 倍。并发上限取 32, 不是拍脑袋定的: 先广档扫过 8 / 16 / 32 / 64 / 128 / 256, 再细扫几档, 32 起进入平台区, 更大的值不再更快, 只让「冷缓存与网络盘上的抖动面」变宽, 于是取平台区起点。原生递归候选 (`native`) 的落选原因不是慢, 是跟契约的硬冲突: 它本想用 `fs.readdir` 的 `recursive` 模式, 实测 (bun 1.4.2 与 node 26 双载体) 却发现那条路会跟进符号链接、遇到首个不可读目录就中断整次调用, 两条都碰了红线。

体积统计的裁定结果形状不一样, 叫「策略 A 双轨」: 不是选一个, 是两个都留, 按环境分流, 有 `du` 的平台走快路径, 没有的走纯实现。两轨的口径不同, 但各自对齐所在平台的原生直觉: `du` 报磁盘占用 (与 Finder 一致), 纯实现报逻辑字节 (与 Explorer 的「大小」列一致)。基准里, `du` 在合成场景约 11 倍于纯实现。裁定记录见 [扫描与体积](scan-and-size.md)。

落选的候选没有被删掉。三个扫描实现都留在仓库里, 继续参加每一轮契约用例与基准: 既留着下一次改判的余地, 也让每次基准都有现成的对照组。

需要说清候选制不是什么: 它不是运行时插件系统, 也不是留给用户的口味选项。它是开发期的决策程序, 候选的增删是代码改动, 胜出者由门面写死 (`scan.ts` 一行导出)。唯一的例外是体积统计, 那个二选一发生在运行时, 但依据是环境探针 (`findDu()` 能不能找到 `du`), 不是用户偏好。

把它想成选角: 同一个角色排几个演员, 用同一份剧本 (行为契约) 与同一批考题 (基准) 逐个考, 成绩单说了算, 不靠印象; 落选的演员留在团里, 下轮改戏再竞争。基准环节还有一道前置校验, 挺能说明这套东西的性格: 计时之前先核对各候选的命中数是否一致, 不一致直接报「数据不可比」并中止。先证明大家在解同一道题, 再比谁解得快。

## 设计模式: 六个落点

代码里能指出六处成型的设计模式, 都有具体落点:

| 模式                          | 落点                          | 一句话                                                               |
| ----------------------------- | ----------------------------- | -------------------------------------------------------------------- |
| Facade 门面                   | `src/scan.ts` / `src/size.ts` | 对外只暴露胜出的实现, 换实现只改一处                                 |
| Strategy 策略                 | 候选制本身                    | 五个候选实现同一套 `Scanner` / `Sizer` 接口                          |
| Adapter 适配器                | `src/runtime.ts`              | Bun 与 Node 的差异收敛在一个文件里                                   |
| Dependency Injection 依赖注入 | `src/init.ts`                 | 文件系统与交互 IO 全部经 `InitDeps` 注入                             |
| State Machine 状态机          | `InitResult`                  | 向导的出口是三态显式: `written` / `cancelled` / `declined-overwrite` |
| Discriminated Union 判别联合  | `LoadConfigResult`            | 按 `state` 字段分流 `ok` / `absent`, 编译器盯着调用方处理每一支      |

其中两个不止出现在表里那一处, 而是贯穿多个模块, 值得多讲一句。

「依赖注入」在这里没有框架, 就是把环境依赖变成显式参数。向导模块 (`init.ts`) 不直接碰 `stdin` 与文件系统, 文件存在性判定、写文件、交互输入全部经 `InitDeps` 进来, 测试可以注入假实现; 配置模块的路径解析把 `platform` / `homedir` / `env` 做成可注入参数; 渲染模块明写「保持纯函数, 不读环境」, 家目录缩写与路径风味都由调用方传入。收益是具体的: 在 macOS 上注入 `platform: 'win32'`, 就能直接跑 Windows 的路径判定与配置位置, 不需要一台 Windows 机器。

「判别联合」的用法是结果不带猜的空间: 配置装载只有两种结局, 拿到配置 (`ok`) 或文件不存在 (`absent`), 没有「先拿到 null 再想办法」的中间态; 向导只有三种结局, 每种后续文案不同, 编译器会盯着调用方把分支写全。常见的做法是返回一个 boolean「成功没」, 调用方回头猜「是取消还是拒绝」; 这里把状态显式做进了类型里。

模式表之外还有一条贯穿的惯例: 模块对外一律以 `createXxx()` 工厂函数交出实例, 不导出类; 数据形状由 `interface` 描述。零依赖加上这套写法, 让「对象」在这个仓库里始终是普通数据结构, 而不是需要理解继承链的实例。

顺带说一句, 标注这些模式名是本文干的。「门面」与「依赖注入」是代码注释自己用的词, 其余几个名字是给读者用的路标, 不是作者按图施工的图纸。

## 数据结构: Map、Set 与排序

零运行时依赖 ([ADR 0003](../adrs/0003-zero-runtime-deps.md)) 有一个安静但彻底的后果: 没有外部数据结构库可用。翻遍 `src/`, 数据容器只有三样: `Map`、`Set`、数组, 加上一批由 `interface` 定义形状的普通对象。

三样工具各司其职: `Set` 管成员判定 (排除 / 包含名单、已见根、安全闸的已见目标); `Map` 管「键到值」的索引与去重 (命中集合、名单命中计数、删除结果回填); 数组排序只干一件事, 把遍历或并发打乱的结果重新钉成确定的输出序。

三个细节值得停一下。

**去重键不是路径本身**, 而是「realpath 归一加 Windows 大小写折叠」之后算出来的值 (`guard.ts` 的 `dedupeKey`)。这一手同时解决两件事: 同一目录的多种写法 (符号链接、大小写) 只算一次; 而这个键与删除安全闸同源, 扫描与安全闸对「重复」的判定不会再打架。数据结构的键直接编码业务语义, 这是全仓最讲究的一处。

**输出与完成次序解耦**。有界并发扫描的完成顺序本是不确定的, 但清单必须确定, 所以命中集合最后统一按 target 升序排序才出结果, 比较用码元序, 不依赖 locale。并发只影响到达的先后, 不影响输出。

**递归换成显式栈**。并发候选不写递归, 待遍历的目录压在数组栈上 (`stack.pop()`), 池内同时在飞的任务数封顶。效果是 200 层深的嵌套目录也不吃函数调用栈; 「对子树无界并发」的 promise 爆炸从结构上就不可能出现。没有自定义的树或图: 目录树边走边处理, 不需要先建出来。

## 设计原则: 代码里读得出的信条

第一组信条关乎模块边界: 依赖倒置、单一职责、纯函数优先。三个名字听着像教科书习题, 落到这个仓库其实是同一件事的三个面: 让模块的行为完全由显式输入决定。调用方只依赖接口, `cli.ts` 调 `createScanner()` 时, 并不知道背后是哪个候选; 每个模块只做一件事, `cli.ts` 不实现任何业务, 名单的静默剔除收在「合并收口处」这一处, 而不是让三个扫描候选各改一遍判定; 模块尽量不读环境, 渲染函数「入参决定全部输出」, 平台风味在模块加载时定格一次, 调用期不再读环境。

第二组只有一位: 不做。设计文档有一节就叫「明确不做 (YAGNI)」, 列着交互勾选、活跃度智能推荐、`--json` 输出、体积阈值过滤, 以及其他清理能力与共享基础库的抽取, 末了一句「以上均等真实需要出现时再议」。弃用理由写得很具体, 例如放弃「按项目多久没动过来预勾选」: 「`node_modules` 自身的 mtime 不代表项目使用状态」, 把一个未经验证的启发式规则塞进删除决策链, 复杂度和风险都不成比例。同款克制也约束着基础设施: ADR 里明说共享抽取「到时再议」, 本期不预建。

第三组关乎失败: 失败必须响亮。落地方式是量化的: 退出码只有 0 与 1 两个档次, 但 1 的覆盖面很宽 (删除失败 / 整批中止 / 未测到体积的目标 / 配置损坏 / 参数错误); 清单走 stdout, 诊断走 stderr, 两条流互不污染; 体积测不到的目标不许静默移出清单, 要以占位行留在原地并计入失败; 名单里的名字一个都没命中必须告警, 代码注释把这条反馈通道称「保命名单」; 连 `du` 的英文报错也不许原样透传, 一律翻译成中文告警再出。这套「不得静默」的清单, 是设计总纲里「失败响亮」那条成功标准的逐条物化。

## 契约优先: 先定尺子, 再写实现

这个项目把「拿什么判对错」当作一等公民, 先于实现写好。

验收证据分三层。最里层是代码层的测试 (契约 / 鲁棒 / 压测等几套, 外加按运行时各注册一遍的双载体 e2e); 中间层是 CLI 黑盒的金样本语料, 每条用例是一份输入加一份逐字节的期望输出与退出码; 最外层是性能基准。三层都在回答同一个问题: 这段代码错了的话, 有没有东西会喊。

金样本语料背靠一份编号化行为契约 (BC / OF / EC 三族条款, 见 [行为契约](../protocol/behavior-contract.md))。契约有两条纪律很关键: 每条语料的期望必须能由条款原文推演辩护, 「严禁『跑一遍记下来』式捕获」; 语料只增不改既有期望, 要改就得先过「三向定责」(修语料、修契约还是修实现), 写明依据再动。条款与语料的现行规模不写死在本文里, 以契约文件与 [覆盖表](../protocol/conformance/coverage.md) 的实时内容为准。

验收器是确定性、零 AI 的, 且语言中立: 被测命令只是一个参数, 从黑盒面收放 (argv / env / stdin 进去, stdout / stderr / 退出码 / 文件系统终态出来)。换句话说, 未来的 Rust 版或 C 版实现, 可以拿同一套语料做机械验收, 验收器不看它内部怎么写。这是为将来可能的重写准备的 (TS 只是参考实现, 未来可能以 Rust / C 等语言重写, 见 [ADR 0008](../adrs/0008-transcription-kit.md)): 没有它, 每次转写都会退化为「看着 TS 重抄一遍」, 行为漂移无法察觉。

还有一道反向保险: 变异自证。故意往实现里注入缺陷 (剪枝谓词取反、退出码吞掉、排序缺失之类), 看语料抓不抓得住; 抓不住的语料不算数。覆盖率问的是「这行代码跑过没有」, 变异自证问的是「这段代码错了的话, 有没有东西会喊」, 后者狠得多。

这套体系也不装作万能: 覆盖不到的地方显式豁免、写明理由, 例如需要竞态时序缝的 (目标在校验与删除之间消失)、需要 Windows 宿主机的 (平台路径矩阵)、成本不划算的 (真写满 1 GiB 数据去测大档展示)。豁免清单本身就是一张「已知哪里有护栏缺口」的诚实账。

## 代价: 这套结构的账单

候选制的维护成本是真实的。同一套语义判定要写三遍 (三个扫描候选各一遍), 三份要同步演进。一个真实的分歧: 名单里直接写 `node_modules` 时 (正常路径上它会被配置层的合并收口提前剔掉, 但候选自己并不知道这条上层约定), 后过滤的 `native` 候选会把全部命中拒掉, 两个剪枝候选照常记录, 同一输入, 结论相反。契约用例用同一套尺子跑全部候选, 但尺子上没有这一格, 分歧不会报警, 靠上游的静默剔除兜着。可替换性是花钱买的, 这笔钱付在「同一语义写三遍, 三份要同步」上。

对个人小工具来说, 这套结构偏重。一个删除 `node_modules` 的工具, 二十来个源文件、五个候选实现, 最终的产出是一个扫描器与一群体积统计器, 选择与维护的开销花在了「选」这个过程自身。作者对这一点有自觉, 并在 [ADR 0001](../adrs/0001-workspace-level-cleaner.md) 里提前认账: 基础设施共享到时再议, 本期不预建。

无框架的账单也得有人付。手写 ANSI 渲染 (色块视觉规范是自制的, 连终端列宽都要按 CJK 双宽自己算)、手写参数解析、自制金样板断言器, 为什么自制? 因为 bun 内置快照的样板目录被硬编码在测试文件同级, 官方不提供配置入口 (仓库里记为「文档与二进制探针双证」); 于是几十行自己写, 换来语义化的样板名与可直接 diff 的文本。零依赖换来的是干净的运行路径: 没有依赖树、没有升级负担、开发态无构建; 代价是这些活全部自己干。

这三笔账不是控诉, 是发票。它们买到了东西: 性能决策有据可查、行为可被机械验收、运行路径没有依赖树。值不值, 取决于怎么给这三样定价; 本文不代为定价。

回到开头那句判断: 这套代码的重心不在「删」, 在「凭什么说它删得对」。现在可以把它说得更完整了。这套代码的每个结构, 都在回答同一个问题:

> 如果我错了, 谁会知道?

答案是机械的回答, 不是人的回答。性能错了, 基准会知道; 行为漂了, 语料会知道; 删除目标不合法, 安全闸根本不放它过去; 名单写错、体积测不到、删除失败, 都有告警或非零退出码在喊。机械的回答有两点好处: 它不需要记忆, 也不需要自觉。

这套结构不是通例, 也不该被当通例抄。这套代码值得这些花费, 是因为两个前提同时成立: 有一个几万目录的真实工作区要反复跑 (性能要有据), 有「未来可能换语言重写」的预期 (行为要可被机械验收)。前提缺一个, 这张账单就会显得比收益大。

毕竟, 一个删除工具最不能有的品质, 就是自信。
