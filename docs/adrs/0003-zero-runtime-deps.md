## 上下文与问题陈述 (Context & Problem)

工具是跨机个人 CLI, 其需求 (文件系统、子进程、readline、ANSI 转义) 与运行时内置能力高度重合。引入第三方运行时依赖要付出三样成本: 供应链与安全面、随上游漂移的升级维护、分发链路里的依赖树。需要确定依赖与构建策略的边界。

## 被放弃的替代方案 (Options Considered & Rejected)

**[引入第三方工具库 (chalk / commander / glob 一类)]**

放弃理由: 本项目 CLI 面很小 (一个主命令 + 一个子命令 + 几个旗标), 颜色与参数解析手写规模可控; 扫描是高度定制的行为 (命中剪枝、排除名单、符号链接策略), 通用库的默认行为反而要逐个绕开。用一棵依赖树换这几百行, 不划算。

**[引入表格渲染 / 进度条一类便利包]**

放弃理由: 输出规格追求紧凑清单, 自制渲染数十行即可; 便利包带来的传递依赖与版本锁定成本大于收益。

**[引入构建工具 (打包 / 转译链)]**

放弃理由: 两侧运行时都原生直跑 TypeScript (见 [ADR 0006](0006-dual-runtime-bun-first.md)), 构建步骤只会增加「改完要重跑构建」的摩擦; 无依赖可捆, 无产物可管 (该判断的适用范围已被 [ADR 0009](0009-npm-distribution-form.md) 收窄: npm 分发态需要一次 `bun build`, 开发运行路径不受影响)。

## 决策结论与选择原因 (Decision & Why)

1. **运行时零依赖**: 运行路径上的代码只 import 运行时内置模块 (`bun:` / `node:`) 与相对路径模块, 不引任何第三方包; ANSI 颜色与参数解析手写。
2. **零构建**: 源码直跑, 无产物, 无打包步骤, 改完即生效 (已被 [ADR 0009](0009-npm-distribution-form.md) 局部取代: 开发运行路径仍零构建, npm 分发态产出编译产物)。
3. **边界: 开发工具链不受限**: devDependencies (oxlint / prettier / lefthook / typescript 等) 不进运行路径, 不属本条约束; 但它们一律精确锁定版本 (见 [ADR 0005](0005-engineering-gates-and-hooks.md))。

选择原因: 依赖为零则供应链面、升级负担、构建步骤同时归零, 这是个人小工具档位下最低的长期维护成本。

## 后果与权衡妥协 (Consequences & Trade-offs)

**正面收益**

- 无供应链面、无依赖升级、无锁文件漂移、无构建步骤。
- 代码全部是业务逻辑, 评审面小。

**权衡妥协**

- 个别能力需手写 (参数解析、ANSI 渲染), 规模受限于 CLI 面大小; 若 CLI 面显著增长, 需重估本条。

## 验证方式与关联引用 (Validation & References)

**验证口径 (实现落地后核验)**

1. 静态核验: 扫描 `src` / `bench` / `scripts` 下全部 import 源 (即 tsconfig 的 include 全域), 只允许 `bun:` / `node:` 前缀与相对路径, 出现第三方包名即违规;
2. 双运行时直跑: `bun src/cli.ts` 与 `node src/cli.ts` 输出一致 (与 [ADR 0006](0006-dual-runtime-bun-first.md) 共用同一口径)。
